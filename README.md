# pi-delegate

`pi`（[@earendil-works/pi-coding-agent](https://github.com/earendil-works/pi-mono)）向けの、最小構成のサブエージェント拡張です。公式サンプル `examples/extensions/subagent` を土台に、エージェント定義（役割・システムプロンプトの概念）と parallel モードを取り除き、「独立した文脈でタスクを委譲する」`delegate`ツールだけを残しています。単発のタスクに加えて、複数ステップを固定順序で流す実行にも対応しています。

## 提供するツール

`delegate`、`handoff_write`、`handoff_read`、`handoff_list` の4つです。ただし**すべてが常に登録されるわけではありません**（後述の「委譲の深さ」を参照）。

### `delegate`

| パラメータ | 必須 | 説明 |
|---|---|---|
| `tasks` | ○ | タスク文の配列（1件以上）。1件なら単発、複数なら固定順で1件ずつ実行 |
| `cwd` | - | サブエージェントを実行する作業ディレクトリ（省略時は呼び出し元と同じ） |

エージェント名・役割・システムプロンプトといった概念はありません。呼び出すたびに、素の`pi`エージェントへタスク文だけを渡します。

### `handoff_write` / `handoff_read` / `handoff_list`

ステップ間でデータを受け渡すための3つのツールです。詳細は後述の「ステップ間のデータ受け渡し」を参照してください。

## 動作の仕組み

`delegate`が`tasks`の各要素を処理するたび、内部で以下のコマンド相当の子プロセスを起動します。

```
pi --mode json -p --no-session [--model <継承したモデル>] [--thinking <継承したレベル>] "Task: <task>"
```

- **`--no-session`**：子プロセスは呼び出し元の会話履歴を一切読み込みません。親のコンテキストは引き継がれない、固定の挙動です。セッションファイルも作られません（エフェメラル）。
- **モデル / thinking レベル**：呼び出し元セッションの現在値（`ctx.model` / `ctx.thinkingLevel`）をそのまま子プロセスに渡します。ステップごとに異なるモデルを割り当てる、といった概念は実装していません。
- **`--mode json`**：子プロセスの標準出力を NDJSON イベントストリームとして受け取り、1行ずつパースします。`message_end` / `tool_result_end` イベントを見つけるたびに `onUpdate` を呼び、ツール実行中の表示を親の TUI に流し込みます。呼び出し中に画面が固まることはありません。
- **中断**：`delegate`呼び出し自体が中断された場合（例：Ctrl+C）、実行中の子プロセスへ `SIGTERM` を送り、5秒待っても終了しなければ `SIGKILL` します。中断は例外ではなく「中断された結果」として返すため、**それまでに完了したステップの内容と使用量は保持されます**。

## 委譲の深さ

**サブエージェントは、さらに委譲することができません。**

環境変数`PI_DELEGATE_DEPTH`で階層を数え、上限（現在は1＝子まで）に達した階層では**`delegate`ツールそのものを登録しません**。実行時にエラーを返すのではなく、呼べるツールが存在しない状態にしています。

理由は、並列実行を持たないためです。各階層が3ステップを出すとすると、深さ1で12プロセス、深さ2で39プロセスとなり、これが全て順番に実行されます。しかも`delegate`は全ステップ完了まで親に戻らないため、**深さが1段増えるごとに「親が介入できない区間」が乗算で伸びます**。加えて、孫の動作は親の画面に「子が`delegate`を呼んだ」という1行として畳まれ、追跡できなくなります。

同じ理由で、**`handoff_list`も子には登録しません**。run 全体を検査するのは親の役割で、子は自分のタスクに集中すれば足ります。

結果として、子プロセスに登録されるのは `handoff_write` と `handoff_read` の2つだけです。子のコンテキストも、その分だけ軽くなります。

## 継承されるもの／されないもの（重要）

子は別プロセスの素の`pi`です。親から明示的に渡しているのは**モデルとthinkingレベルだけ**で、それ以外は「子が自分で設定ファイルを読み直した結果、たまたま親と一致する」という構造になっています。この違いは、ずれた時に効いてきます。

### 明示的に渡しているもの

| 対象 | 方法 |
|---|---|
| モデル | `ctx.model`から`provider/id`を組み立てて`--model`で指定。セッション中に`Ctrl+P`等で変更していれば、その時点の値が渡ります |
| thinkingレベル | `ctx.thinkingLevel`を`--thinking`で指定 |

### 子が自分で読み直すもの（結果として一致する）

- **モデル設定**（`models.json`）：`contextWindow`、`maxTokens`、`reserveTokens`、`keepRecentTokens`、`baseUrl`、`apiKey` など。親から渡してはいませんが、子も同じ`~/.pi/agent/models.json`を読むため一致します。
- **パッケージ／拡張**（`settings.json`の`packages`）：親と同じ一式が読み込まれます。
- **MCPサーバー**：`pi-mcp-adapter`等を使っている場合、設定はファイル（グローバルの`mcp.json`、プロジェクトの`.mcp.json`など）から解決されるため、**親に追加したMCPサーバーは子からも使えます**。ただし**各ステップの子プロセスが、それぞれ自分のMCP接続を張ります**（stdioサーバーならステップごとにサーバープロセスが起動します）。ステップ数だけ起動コストがかかる点に注意してください。
- **ツール一式**：`delegate`は子プロセスに`--tools`を渡していません。したがって子は、**呼び出し元セッションが「今その瞬間に」使っているツール集合を引き継ぐのではなく**、`settings.json`から解決される、素の`pi`起動時と同じデフォルトのツール一式を使います（前述のとおり`delegate`と`handoff_list`を除く）。

### 継承されないもの

- **親の起動時CLIフラグ**：`--model` / `--thinking` 以外は引き継がれません。`--api-key`、`--system-prompt`、`--append-system-prompt`、`--tools`、`--exclude-tools`、`--no-builtin-tools`、`--no-extensions` などで親を起動していても、**子は素の状態で立ち上がります**。特に`--api-key`で一時的なキーを使っている場合、子は設定ファイル側のキーを使う点に注意してください。
- **`cwd`を指定した場合の、プロジェクトローカル設定**：子は指定されたディレクトリで起動するため、そこに`.pi/settings.json`や`.mcp.json`があれば**そちらが適用されます**。親と異なるプロジェクトを指した場合、モデル・ツール・MCPサーバーのいずれもずれる可能性があります。

親の起動オプションを子に揃える制御は、実装していません（`process.argv`を解析して転送すれば部分的には可能ですが、`pi`のフラグ解析を二重に持つことになり、本拡張が担うには重すぎると判断しました）。

## 複数ステップの実行（`tasks`に2件以上）

```json
{ "tasks": [
  "関連ファイルを調査して、handoff_writeで結果を保存して",
  "handoff_readで調査結果を取得し、それをもとに計画を立てて実装して"
]}
```

- `tasks`は`for`ループで**1件ずつ順番に**実行します（各ステップが独立した子プロセス＝独立した文脈）。
- 途中のステップが失敗（exit code 非0、または`stopReason`が`error`/`aborted`）すると、そこで全体を停止し、何ステップ目で失敗したかを報告します。
- 実行の主体は`delegate`ツールの`execute()`内の普通のコード（`for`ループ）であり、**親エージェント（LLM）はステップの合間に一切介在しません**。親が行うのは「全ステップを1回のツール呼び出しとして発行する」ことだけで、各ステップの結果を見て計画を変える、といった動的判断はできません。
- **固定長・直線・1周のみ**です。条件分岐・繰り返し（リトライ）・循環（前のステップに戻る）は出来ません。そうした制御構造が必要な場合は、配列という宣言的な形では表現できず、任意のコードを書ける別の仕組みが必要になります。本拡張はそこまでは踏み込んでいません。

## ステップ間のデータ受け渡し（`handoff_write` / `handoff_read` / `handoff_list`）

各ステップは記憶を共有していないため、あるステップの具体的な出力を次のステップに渡したい場合、`{previous}`のような自動置換は用意していません。代わりに、専用のDB経由で明示的に受け渡します。

- **保存先**：`node:sqlite`（Node標準組み込み、追加依存なし）。
- **DBファイルは、トップレベルの`pi`プロセスごとに1つ**です。パスは `~/.pi/agent/extensions/delegate/sessions/<pid>-<起動時刻ミリ秒>.db`。`delegate`が初めて呼ばれた時に作られます。
- **スキーマ**：`runs`テーブル（run id の採番用）と、`handoff`テーブル（`run_id`, `content`, `created_at`）。`created_at`は**Unixミリ秒（INTEGER）**で保存し、表示時に`2026-09-12T14:03:11.123Z`形式へ変換します。
- **run idの発行**：`delegate`が呼ばれるたびに、そのセッションのDB内で連番を発行します。セッション単位なので`1`, `2`, `3`…と小さい値に収まります。この値を子プロセスの環境変数`PI_DELEGATE_RUN_ID`として渡すので、**ステップ内から`handoff_write`/`handoff_read`を呼ぶ場合、run idを指定する必要はありません**（ツールの`execute()`が環境変数から解決します。LLMの引数としては現れません）。
- **親（トップレベルセッション）から使う場合**：環境変数が無いため、`runId`を明示的に渡します。**実際に`handoff_write`が使われた場合のみ**、`delegate`の結果に`(handoff run: <id>)`が付きます（単発・複数、成功・失敗を問わず同じ判定です）。それを`handoff_list(runId)`に渡せば、各ステップが何を保存したかを時系列で確認できます。

### `handoff_read`は「直前の1件」だけを返します

`handoff_read`が返すのは、その run で**最後に保存された1件**です。3ステップ以上で、さらに前の内容も引き継ぎたい場合は、各ステップに「自分の結果に加えて、前段から受け取った必要な情報も含めて保存せよ」と指示してください（リレー方式）。何を次へ渡すかをステップ自身に判断させるほうが、全件を機械的に積み上げるより結果も良くなります。

なお、取りこぼしがあっても、親は`handoff_list`で全件を事後確認できます。

### 重要：子は「自分がdelegateされたステップだ」と自動的には理解しません

子プロセスのシステムプロンプトは、`pi`を単体で起動した時と完全に同じです（エージェント定義やシステムプロンプト注入の仕組みは持っていません）。`PI_DELEGATE_RUN_ID`環境変数は`handoff_write`/`handoff_read`の`execute()`（LLMから見えないサーバ側コード）が読むだけで、**LLM自身の会話コンテキストには一切現れません**。

つまり、あるステップが`handoff_write`で結果を保存するかどうか、次のステップが`handoff_read`で読みに行くかどうかは、**完全に親が各ステップの`task`文にどう書いたか次第**です。`"Xを調査して"`とだけ書けば、子は普通に調査して回答するだけで、次のステップのために何かを保存しようとはしません。連携させたいなら、`task`文に「handoff_writeで保存して」「handoff_readで取得して」と明示する必要があります。

### DBファイルの削除

自動削除は行いません。不要になったら手動で削除してください。

```
rm -rf ~/.pi/agent/extensions/delegate/sessions
```

実行中の`pi`セッションが無い状態であれば、ディレクトリごと削除して問題ありません。次回の`delegate`呼び出し時に作り直されます。

なお、本ドキュメント中の `~/.pi/agent` は既定値です。`PI_CODING_AGENT_DIR` を設定している環境では、そのディレクトリ配下に読み替えてください（本拡張は `getAgentDir()` の戻り値を使います）。

## 実行は同期・直列（真の並列実行はありません）

`pi`本体のツール実行ループは、1回のアシスタントのターンに複数のツール呼び出しが含まれていても、`for`ループ＋`await`で**1件ずつ順番に**実行します（`packages/agent/src/agent-loop.ts` の `executeToolCalls`）。これは`pi`コア側の挙動であり、この拡張固有のものではありません。

そのため：

- `delegate`の実行中（複数ステップなら全ステップ完了まで）、親エージェントのターンはそこで止まり、完了を待ってから次に進みます。
- 同時に複数の`delegate`呼び出しを走らせたい場合、LLMが同じターンで複数回`delegate`を呼び出したとしても、それらは並列にはならず順番に実行されます。

**この逐次性は、DBの設計前提でもあります。** 1つのDBファイルを共有するのは同一プロセスツリー内だけで、そのツリー内では常に1プロセスしか動いていないため、同時書き込みが原理的に発生しません。独立した`pi`セッションはそれぞれ別のファイルを持つため、互いに干渉しません。したがってロック待ちやWALの設定は不要です。

なお本拡張は、`pi`本体がツール呼び出しを逐次実行することを前提としています。

公式サンプルにあった `tasks`（並列モード。名前が同じですが別物です）と、そのための`MAX_PARALLEL_TASKS` / `MAX_CONCURRENCY` といった同時実行数の制御は、この用途では不要と判断し削除しています。

## エラーの扱い

例外を投げません。DB操作を含め、失敗はすべて戻り値（Result）で表現し、ツールの結果として`isError`で返します。

親に返る文面は次の形に統一しています。

```
Delegate aborted.                                  中断・単発
Delegate aborted at step 2/3.                      中断・複数
Delegate failed: <メッセージ>                       失敗・単発
Delegate failed at step 2/3: <メッセージ>           失敗・複数
```

handoffが使われていた場合は、末尾に`(handoff run: 3)`が付きます。ユーザーによる中断を「失敗」とは呼び分けています。

## 表示

`renderCall` / `renderResult` を実装しており、以下を表示します。

- 実行中：タスク文のプレビュー（複数ステップ時は各ステップのプレビューを最大3件、進捗は「running step i/n」）
- 完了後（折りたたみ表示）：使用したツール呼び出しの一覧（単発は最大10件、複数ステップはステップごとに最大5件）、使用量（トークン数・コスト。複数ステップは合計も表示）
- 完了後（展開表示 `Ctrl+O`）：タスク全文、ツール呼び出し全件、最終出力（Markdown レンダリング）、使用量（複数ステップはステップごとに表示）

## 公式サンプルからの変更点

`@earendil-works/pi-coding-agent` の `examples/extensions/subagent` を土台にしていますが、以下を取り除いています。

- エージェント定義の概念（`agents/*.md`、`discoverAgents()`、`agentScope`、プロジェクトローカルエージェントの信頼確認ダイアログ）
- `tasks`（並列モード）とその表示ロジック
- エージェントごとのシステムプロンプト注入（`--append-system-prompt`）
- ステップ間の自動データ受け渡し（`{previous}`置換）— `handoff_write`/`handoff_read`という明示的なDB経由の仕組みに置き換え

残したもの：子プロセス起動・NDJSONストリーミング・`onUpdate`によるライブ更新・`renderCall`/`renderResult`によるターミナル表示・Ctrl+C時の中断伝播。連鎖実行（複数ステップを1回の呼び出しで宣言し、親を介在させず実行する）という考え方自体は残しつつ、`{ agent, task }`配列をタスク文の配列に単純化しています。

## インストール

```sh
pi install https://github.com/high-u/pi-delegate
```

`~/.pi/agent/settings.json` の `packages` に追加されます。プロジェクトローカルに入れる場合は `-l` を付けてください（`.pi/settings.json` に書かれます）。

更新と削除は次のとおりです。

```sh
pi update https://github.com/high-u/pi-delegate
pi remove https://github.com/high-u/pi-delegate
```

### 開発時（ローカルのクローンを直接使う）

クローンしたディレクトリを、絶対パスまたは相対パスで `packages` に追加します。

```json
{
  "packages": [
    "/path/to/pi-delegate"
  ]
}
```

ローカルパスの場合はコピーが行われず、そのディレクトリを直接参照します。`extensions/*.ts` を編集すればすぐに反映されます（ビルド不要）。

## テスト

`node --test`（Node標準）を使います。テストフレームワークへの依存はありません。

```
node --test "tests/*.test.ts"
```

初回のみ、`pi`本体のパッケージを解決できるようにシンボリックリンクを張ってください（`package.json`は置いていません。`pi`のパッケージ解決に影響させないためです）。

```sh
G=$(npm root -g)/@earendil-works
mkdir -p node_modules/@earendil-works
ln -sfn $G/pi-coding-agent node_modules/@earendil-works/pi-coding-agent
for p in pi-tui pi-ai pi-agent-core; do
  ln -sfn $G/pi-coding-agent/node_modules/@earendil-works/$p node_modules/@earendil-works/$p
done
ln -sfn $G/pi-coding-agent/node_modules/typebox node_modules/typebox
```

対象は、壊れても静かに間違った結果を出す箇所に絞っています。

| ファイル | 対象 |
|---|---|
| `tests/pure.test.ts` | 親に返す文面と表示を決める純粋関数（`getFinalOutput`の全テキストパート連結、NDJSONの不正行の握り潰し、使用量の集計、スナップショットの独立性、失敗判定） |
| `tests/env.test.ts` | 環境変数から解決する`run id`と深さ（明示引数の優先、整数以外の拒否） |
| `tests/registration.test.ts` | 階層ごとのツール登録（子に`delegate`と`handoff_list`が渡らないこと） |
| `tests/handoff-db.test.ts` | 実際のSQLiteファイルに対する読み書き（連番、run間の分離、最新1件、順序、保存の有無、破損時にthrowしないこと） |

`runDelegate`（子プロセス起動）と表示系の整形関数はテストしていません。前者は実際に`pi`を起動する統合テストになり、後者は壊れても目視で分かるためです。
